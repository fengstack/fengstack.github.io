从 Vibe Coding 到双轨 SDD：大模型时代的现代 Agent 编程工程化实践

2026-10 · 由 me 发布 · Agent 编程架构范式与实战复盘 · Spec-Driven & TDD

近年来，随着各类 Coding Agent（Cursor、Windsurf、Claude Code、Aider 等）的普及，以 Andrej Karpathy 为代表提倡的 “Vibe Coding（凭感觉编程）” 风靡技术社区——“不需要看代码细节，甚至不需要严密设计，只要向 AI 描述你的大致意图，让模型自主写码狂奔即可”。

对于个人玩具项目、一次性 Demo 或绿色脚手架探索，Vibe Coding 确实带来了颠覆性的爽感。然而，一旦踏入真实严肃的生产级工程（Brownfield Codebase，已有复杂系统），纯粹靠聊天驱动的 Agent 编程迅速露出了破绽：

  • 上下文漂移（Context Drift）：对话轮次一多，Agent 迅速遗忘最初的架构契约与非功能约束，按下葫芦浮起瓢；
  • 破坏性盲改（Scope Creep）：让 Agent 修复一个边缘逻辑，它却自作主张重构了周围的无关函数，甚至悄悄删掉生产环境必需的异常捕获；
  • 客观真理缺失（Ground Truth Deficit）：Agent 充满信心地向你报告“代码已为您完美实现”，实际上一跑就崩溃，陷入“报错 → 盲目修复 → 引发新隐患”的无限死循环。

事实证明：生产级 AI 编程的瓶颈从来不是大模型的智力不足，而是缺少一套能将 Agent 约束在工程轨道上的全新交付流水线。在过去大半年的高强度项目交付中，我们经历了一场从“重型装甲防御”到“按复杂度分流”的认知跃迁。本文旨在系统复盘这套以 SDD（Spec-Driven Development，规范驱动开发）为灵魂、TDD 为机器裁判、基于复杂度路由的双轨交付体系。

一、演进回溯：为什么早期我们必须依赖 OpenSpec + Superpowers？

回溯到约半年之前（主流模型推理能力与上下文保持尚未完成质变的前夜），用 Agent 处理工业级代码犹如“与醉汉同行”——模型极易发散、容易在复杂的业务上下文里产生幻觉、且极其缺乏耐性，喜欢偷懒省略逻辑。

为了让 Agent 在大型项目中不翻车，业界演化出了一套“重型外骨骼装甲”组合拳：OpenSpec + Superpowers。

【早期重型防御体系链路 (Heavy Armor)】
模糊业务诉求
   ↓
Superpowers Brainstorming (多轮意图澄清 / 方案推演 / 权衡取舍)
   ↓
硬门禁 Hard-Gate (人类必须显式确认技术方案，否则绝不动代码)
   ↓
OpenSpec 规约化 (写入系统级 Spec: 契约/数据模型/状态机/边界)
   ↓
Subagent-Driven 执行 (主代理做 Tech Lead，派生子代理隔离编码与自验)

1. OpenSpec：建立机器与人类对话的“系统宪法”

自然语言是充满歧义与漏洞的。如果你对 Agent 说“帮我给 RPC 框架加一个自适应熔断器”，Agent 会凭借概率分布随机挑选一种算法草草实现，完全忽略你既有的指标收集器、配置中心和线程模型。

OpenSpec 的核心价值，就是将业务意图沉淀为结构化、版本化的工程规范（Single Source of Truth）：

  • 明确定义 数据模型（Schemas） 与 接口契约（API Contracts）；
  • 明确划分 系统边界（In-Scope 必须做 / Out-of-Scope 绝不触碰）；
  • 明确固化 非功能性指标（吞吐、延迟、内存占用、向后兼容性）。

在这一模式下，Spec 是人机协作的唯一法定基准。没有 Spec，就不存在可以被度量的“正确性”。

2. Superpowers：行为状态机与硬门禁（Hard-Gate）

有了 Spec 还不够，因为 Agent 会“抢跑”——往往在需求还没想清时就急着敲键盘。以 Superpowers 为代表的工程插件，给 Agent 套上了严格的行为状态机与硬门禁：

  • 强制头脑风暴（Brainstorming）：在动笔前，强制 Agent 探究动机、梳理限制、给出 2~3 种技术选型与权衡；
  • 硬门禁（Hard-Gate）法则：在人类明确批准设计之前，严禁 Agent 触碰任何源码或调用脚手架；
  • 角色分离（Subagent 隔离）：主代理充当 Tech Lead / Reviewer，子代理隔离在独立分支或上下文做脏活，防止主上下文被海量代码污染。

二、转折与反思：模型变聪明了，“全套重装”为何显得过重？

然而，随着最新一代基座模型（具备深度思考与长程推理能力的 Coding 模型）的迅猛迭代，开发者的一线体感发生了显著变化：模型变聪明了，曾经引以为傲的重型框架，反而产生了显著的“工程摩擦力”。

1. 重型工具链在日常开发中的内耗

如果今天只是想给接口加一个排序字段、修复一个 NPE、或者给已有枚举类增加一个状态分支，依然要求 Agent：

  1. 走一遍冗长的 Superpowers Brainstorming 问答套话；
  2. 按照 OpenSpec 规范写出几十行格式严苛的 spec.md；
  3. 人工反复确认门禁；
  4. 调度 Subagent 隔离派发任务……

这种“杀鸡用牛刀”的仪式感，不仅消耗了大量 Token 和宝贵时间，更打断了开发者的心流。此时工具不再是助推器，而成了“流程官僚主义”。

2. 务实主义哲学：按需降级（Adaptive Downgrade）

现代软件工程的核心原则从来不是教条主义，而是根据问题复杂度匹配恰当的解决工具。既然现在的模型已经拥有强大的隐式推理和代码理解力，我们就不再需要把每一个需求都塞进“全套重装”里。我们需要的是：保留核心灵魂（规范与测试），但在组织形式上实现“轻重分流”。

三、双轨范式：基于复杂度路由的现代 SDD 开发流

基于上述演进，我们沉淀出了当前最敏捷、可靠的双轨驱动开发矩阵（Dual-Track Matrix）：

分类轨道 典型场景 核心工具组合 Spec 表现形式 门禁与流程
重轨 (Heavy Track) 系统重构、核心架构变更、全新子系统开发、跨模块复杂协同 OpenSpec + Superpowers 宏观系统 Spec（包含 Schema、契约文档、时序图、架构权衡） 严格硬门禁，人工全量审查 Spec，多代理分发执行
轻轨 (Light Track) 局部特性扩展、明确的缺陷修复、既有模式下的常规迭代（占 70%~80%） Plan 模式（极简执行清单） 微观任务 Spec（原子化任务步骤、明确文件路径、验证指令） 快速确认 Plan（15 秒审查），单 Agent 快进快出

1. 复杂轨道（Heavy Track）：OpenSpec + Superpowers 的定海神针

当需求涉及未知领域探索、高风险资金链路、或底层并发原语变更时，绝不能贪图轻巧：

  • 先由 Superpowers 强行展开 Brainstorming，逼迫 Agent 暴露潜在死锁、并发竞争或边界漏洞；
  • 通过 OpenSpec 锁定核心数据流向与错误码体系，将其固化为不可动摇的契约文档；
  • 人类工程师以架构师的身份严格把关文档，一旦通过，后续实现便坚如磐石。

2. 轻轨（Light Track）：Plan 模式的极简敏捷流

对于大多数日常需求，我们将其降级为 Plan 模式。这里的关键心法是：Plan 就是轻量级 Micro-Spec。

跳过繁冗的问答，直接要求 Agent 针对当前需求输出一个结构化的 Implementation Plan，它必须明确三要素：

// 典型的 Plan 模式结构示例：
### Step 1: 编写红测试用例
- [ ] 目标文件: src/test/java/.../CircuitBreakerTest.java
- [ ] 逻辑: 模拟连续 5 次超时，断言状态必须转移为 OPEN 并抛出 CIRCUIT_OPEN
- [ ] 验证命令: mvn test -Dtest=CircuitBreakerTest

### Step 2: 核心状态机最小实现
- [ ] 目标文件: src/main/java/.../CircuitBreaker.java
- [ ] 逻辑: 引入滑动窗口计数器，满足阈值时原子切换 AtomicReference
- [ ] 验证命令: mvn test -Dtest=CircuitBreakerTest (验证转绿)

### Step 3: 回归与代码重构
- [ ] 目标文件: src/main/java/.../CircuitBreakerFilter.java
- [ ] 逻辑: 接入消费端 Filter 链，消除冗余计算
- [ ] 验证命令: mvn clean test (全量回归验证)

开发者花 15 秒扫一眼该清单，确认路径无误、步骤合理，回车确认即可。Agent 按步施工，每步打钩，既敏捷又完全处于可控轨道之中。

四、双核基石：为什么 SDD 与 TDD 永远不可动摇？

在双轨分流中，形式虽然有轻有重，但有两个底层支柱始终贯穿其中，它们构成了 Agent 编程的灵魂：SDD（规范驱动）是方向盘，TDD（测试驱动）是刹车与安全带。

1. SDD 是灵魂：代码只是 Spec 的编译产物

在传统人肉写码时代，代码是第一公民；但在 Agent 时代，规范（Spec）才是真正的第一公民。

很多人误以为只有 OpenSpec 才是 SDD。其实不然，轻轨中的 Plan 模式同样是 SDD！

  • OpenSpec 是系统级的宏观 Spec；
  • Plan 是任务级的微观 Spec。

SDD 的铁律：在任何代码被改动之前，必须先有被确认的 Spec（无论是文档还是 Plan）。代码不应该由 Agent 凭“直觉”随手敲出，代码本质上只是 Spec 在特定编程语言、特定框架约束下的具象化投影。

2. TDD 是机器裁判：给 Agent 装上“客观感官”

大模型本质上是一个基于概率的文本生成器，它天然具备“谄媚性”和“自嗨倾向”——哪怕代码逻辑完全写错，它也能头头是道地写出一番完美解释。

克服大模型自嗨的唯一解法，是引入现实世界的物理定律——在软件世界里，这就是可执行的自动化测试。

在 Agent 驱动开发中，经典的 红-绿-重构（Red-Green-Refactor） 展现出了不可替代的工程威慑力：

  1. 第一阶段：测试先行，必须见红（Red）： Agent 根据 Spec 编写单元测试用例并执行。此时必须失败！如果测试第一次运行就直接通过了，这大概率是个“假测试（False Positive）”。见红才能证明测试真正覆盖了尚未实现的功能漏洞。
  2. 第二阶段：编写最小实现跑通（Green）： 只写满足测试的最少代码，再次运行测试直到全部变绿。此时机器给出了客观确认：代码在功能上已完全符合当前契约。
  3. 第三阶段：审查与重构（Refactor）： 在绿灯护栏的保护下优化性能、重构坏味道，并运行全量回归套件，确保没有搞砸现有历史代码。

当测试全部变绿的一瞬间，无论 Agent 的提示词是什么、推理过程有多曲折，你都可以确认：当前代码在客观上满足了 Spec 定义的契约。

五、主流 AI 编程范式全景横向比对

将我们当前的打法与主流 AI 编程方式进行横向比对，其差异与优势一目了然：

维度 Vibe Coding (直觉流) Cursor / Aider 工具流 早期重型 Multi-Agent 流 现代双轨 SDD + TDD (本文方案)
交互核心 自然语言闲聊对话 提示词 + 手动 @文件 注入 多 Agent 自治对话与长流程 以 Spec/Plan 为中枢，按需路由
交付确定性 极低（依赖模型当天手感） 中等（依赖工程师盯梢程度） 高（但易死锁或过度设计） 极高（Spec 约束边界 + TDD 机器仲裁）
工程摩擦力 几乎为 0（极速开工） 较低 极高（小需求也得走漫长审批） 动态自适应（轻活秒级开工，重活铜墙铁壁）
上下文健康度 极快腐化并遗忘 容易膨胀，需人工清理 频繁分发导致 Token 暴涨 Plan 隔离执行，上下文高度收敛干净
适用场景 独立页面、Demo 玩具 单点修改、脚本小工具 特大架构演进实验 工业级、企业级主流业务开发与交付

六、写在最后：工程师在 Agent 时代的真正核心价值

从 Vibe Coding 的狂欢，到 OpenSpec + Superpowers 的重度防守，再到如今轻重分流的双轨 SDD，这不仅是一套工具链的演进，更是工程师自我认知的深刻迭代：

  • 键盘打字员的价值正在归零：单纯熟记语法、编写 CRUD 样板代码的技能，在强大的基座模型面前已经毫无壁垒；
  • 架构与规约能力（Spec Authoring）成为第一生产力：你能否用严密的思维定义数据模型、划定系统边界、识别隐蔽的边界条件？这是决定 Agent 是产出工业级资产还是数字垃圾的根本分水岭；
  • 工程裁判能力（TDD & Gatekeeping）成为核心守门人：你能否用精妙的测试套件与合理的复杂度路由，既放开 Agent 的生产力狂奔，又牢牢握紧确定性的缰绳？

现代 Agent 编程的终极心法，不是学会多少精巧的 Prompt，而是把软件工程中被验证了几十年的常识——规范先行、计划明确、测试驱动——通过新的交互介质重新贯彻到底。模型越来越聪明，而我们要做的，就是给这个拥有无尽算力与知识的超级外脑，配上一张精确的施工图（SDD），以及一道不可逾越的安全护栏（TDD）。
