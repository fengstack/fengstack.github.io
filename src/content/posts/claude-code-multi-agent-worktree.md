很多 AI 编程演示通常展示一种偏理想化的场景：在干净的新项目里向 Claude Code 提一个需求，几轮终端交互后代码顺利跑通并交付。

但在真实的日常研发中，多需求交织与插队才是常态：
- **需求 A（业务新特性）**：用户中心需要新增批量异步导出，涉及多个模块，需反复调试与联调；
- **需求 B（技术债务）**：核心模块间的公共 API 存在循环依赖，需要重构包结构并保证向后兼容；
- **需求 C（突发线上 Hotfix）**：生产环境偶发异常导致事务未回滚，需要当天排查并提交热修；
- **需求 D（等待外部依赖）**：昨天的支付接口改动还在等待联调，分支暂时挂起。

如果只在项目根目录开一个 `claude` 会话串行推进，通常会遇到几个实际阻碍：
1. **上下文切换成本高**：正在做需求 A 时被插进来的热修打断，退出或重置会话后，原需求的推演细节就丢失了；
2. **分支切换污染本地环境**：在同一个目录下频繁 `git checkout`，不仅要反复暂存改动，编译产物（如 Java 的 `target/` 目录）还会被反复覆盖和重编；
3. **单线程等待拖慢进度**：需求 A 运行一次完整测试通常需要几分钟，此时终端被占用，无法同时推进其他需求。

单 Agent 串行处理很难应对并发任务。更有效的方式是将开发流拆开：通过 **Subagents** 解耦子任务、**Agent Teams** 组织角色接力，并借助 **Git Worktree** 在物理上隔离工作区。

## 一、 企业研发图景：多需求交织的并发场景

在常见的企业协作规范中，Git 分支通常遵循 `main（生产）`、`develop（集成联调）`、`feature/*（业务分支）` 与 `hotfix/*（热修分支）` 的模型：

```text
生产主干 main       ──────────────────────────────────────────●────── (发布)
                                                             ▲
                                                             │
集成主干 develop    ──────●───────────────●──────────────────●────── (联调)
                         ▲               ▲                  ▲
    ┌────────────────────┘               │                  │
    │ [Worktree 1]                       │ [Worktree 2]     │ [Worktree 3]
    ▼                                    ▼                  ▼
feature/batch-export (需求A)       refactor/api-pkg (需求B)  hotfix/tx-null-p0 (需求C)
• 业务开发与契约定义                 • 跨模块循环依赖治理       • 线上紧急事务缺陷修复
• 正在跑长耗时集成测试               • 等待接口定义确认         • 快速定点单测并优先合入
```

在这种协作拓扑下，单 Agent 串行推进的瓶颈主要来自三个方面：

1. **串行排队拉长交付周期**：如果需求 A 耗时较长、热修 C 仅需半小时，单会话模式下紧急修复要么被迫等待前序任务测试跑完，要么强制中断导致前序进度混乱。
2. **外部等待阻塞本地操作**：需求开发经常伴随外部等待（如等待前端定义字段、等待测试环境就绪）。单 Agent 模式下任务一旦挂起，本地会话就容易陷入停滞。
3. **改动混合增加集成风险**：如果把多个需求的改动混在同一个工作区或同一分支中，容易造成提交污染，难以将成熟的需求单独拆出提 PR。

## 二、 物理隔离：用 Git Worktree 支撑多需求并发

在同一个代码目录下多开终端运行 `claude`，往往会遇到文件写入冲突与构建缓存踩踏。要在本地实现并发开发，Git Worktree 是适合的底层机制。

### 2.1 Git Worktree 的运行机制

与直接 `git clone` 相比，`git worktree` 共享底层同一个 `.git` 对象库：
- **创建速度快**：无需重新拉取代码，执行命令后即可签出新的物理目录；
- **存储开销小**：共享所有已有的提交历史与对象；
- **文件系统独立**：每个 Worktree 拥有独立的物理工作目录、独立的 HEAD 指针以及独立的编译输出目录（如独立的 `target/`）。

### 2.2 一键初始化多需求工作区

在冲刺周期开始时，面对看板上的几个并行需求，可以在项目下统一建立 `.worktrees/` 目录：

```bash
# 1. 确保本地主干处于最新状态
git checkout develop && git pull --ff-only

# 2. 签出独立的需求工作空间（基于 develop 分支）
git worktree add .worktrees/feat-batch-export -b feature/batch-export origin/develop
git worktree add .worktrees/refactor-api-pkg  -b refactor/api-pkg origin/develop

# 3. 针对线上紧急热修，基于 main 分支直接签出工作区
git worktree add .worktrees/hotfix-tx-p0      -b hotfix/tx-null-p0 origin/main
```

此时磁盘上的结构如下：

```text
my-project/
├── .git/                      <-- 共享的核心对象库
├── .worktrees/
│   ├── hotfix-tx-p0/          <-- 对应需求 C (分支 hotfix/tx-null-p0)
│   ├── feat-batch-export/     <-- 对应需求 A (分支 feature/batch-export)
│   └── refactor-api-pkg/      <-- 对应需求 B (分支 refactor/api-pkg)
└── src/                       <-- 本地主干工作区 (留在 develop)
```

每个工作区的文件修改与本地编译相互隔离，为多会话并行提供了基础。

## 三、 任务解耦：用 Subagents 隔离需求上下文

有了物理隔离的工作区，接下来的重点是**任务解耦与上下文管理**。

### 3.1 核心原则：一个需求一个独立上下文

在实际开发中，每个需求都有其专属的业务背景、接口规约与受影响模块。如果把需求 A 的数据库字段调整与需求 B 的架构包重命名混在同一个会话中，模型的注意力会被无关代码稀释。

**Subagent 的调度逻辑是：为每个需求派生独立的子会话，仅注入该任务必需的最小上下文，任务完成即汇报收敛。**

### 3.2 实战配置与定向派发

在项目根目录的 `CLAUDE.md` 中，可以写入多需求调度的协作边界：

```markdown
<!-- CLAUDE.md 多需求调度规则 -->
# Multi-Feature Dispatch Guidelines
1. 避免在一个会话内混合处理不同的 Jira 需求。
2. 每个子任务通过对应的 Worktree 执行，改动需局限在该工作区内部。
3. 需求实施前，需在对应 Worktree 内确认或编写单元测试。
4. 完成修改并验证通过后提交局部 commit，不直接向远程 main/develop 推送未测试代码。
```

在不同终端窗口中，可以通过独立的 Claude 实例直接推进各自分支的任务：

#### 终端 1：推进需求 A（异步批量导出特性）
```bash
cd .worktrees/feat-batch-export
claude "【需求 A：用户中心异步批量导出】
目标：
1. 在 user-service 模块中新增流式导出任务调度，替换原先的同步内存拼接；
2. 引入分段分页查询与 CSV 临时流写入，避免大数据量下的内存占用；
3. 对外暴露查询任务进度的 REST 接口。
约束：
- 仅修改 user-service 与 common-dto 模块；
- 完成后在本工作区执行 mvn test -pl user-service 验证，通过后提交 commit。"
```

#### 终端 2：推进需求 C（紧急线上事务热修）
```bash
cd .worktrees/hotfix-tx-p0
claude "【需求 C：修复订单子单异常导致事务未回滚缺陷】
目标：
1. 排查 PlaceOrderService 中 insertOrderItems 的异常捕获逻辑；
2. 修复只记录日志未抛出异常导致外层事务正常提交的问题；
3. 补充针对异常回滚场景的单元测试。
验证要求：
- 在本工作区执行 mvn test -pl order-service -Dtest=PlaceOrderTxTest；
- 确保测试通过并提交 commit。"
```

两个 Claude 实例在各自的物理目录中运行，上下文互不干扰，编译与测试输出也互不抢占。

## 四、 角色分工：Agent Teams 的流水线接力机制

除了纵向的任务隔离，在交付流程上还可以引入角色化分工。一个需求从构思到合入通常经过三个阶段：**影响面分析 → 编码实施 → 架构检验与测试**。

让不同的 Claude 实例承担明确职责，可以在多个需求之间形成**流水线接力（Pipeline Relay）**：

```text
【多需求在 Agent Teams 角色矩阵中的流水线接力】

   时间轴        Audit Agent (审计)      Implementation Agent (开发)     Guard Agent (守卫与测试)
     │
   10:00 ───> [需求 A] 扫描接口契约
     │
   10:30 ───> [需求 B] 分析循环依赖 ───> [需求 A] 编写流式导出代码
     │
   11:00 ───> [需求 C] 定位 P0 缺陷  ───> [需求 B] 实施包结构调整   ───> [需求 A] 运行全量回归测试
     │
   11:30 ───>                     ───> [需求 C] 修复回滚逻辑     ───> [需求 B] 运行架构防腐断言
     │
   12:00 ───>                     ───>                         ───> [需求 C] 验证单测并合入
```

### 4.1 角色一：Audit Agent —— 只读影响面分析

在修改代码前，先由 Audit Agent 在对应工作区进行只读扫描：

```bash
cd .worktrees/refactor-api-pkg
claude -p "你是一名架构审计助手。只读分析整个工程中直接依赖 internal.dao 实体的外部模块。
输出 Markdown 影响面清单，列出因 API 包重构而受影响的 Controller 或外部 Service。
严禁修改任何代码，完成即可退出。" > audit-report.md
```

通过这一步在动工前先摸清受影响的调用方，形成明确的实施清单。

### 4.2 角色二：Implementation Agent —— 聚焦具体实现

有了审计清单后，开发实例进驻工作区。它的任务是按照给定的目标进行最小修改，尽量减少与需求无关的代码调整。

### 4.3 角色三：Guard Agent —— 自动化检验与回归

代码编写完成后，由检验实例运行测试并核验规范：
1. **运行架构守卫测试**（如 ArchUnit 断言）：检查是否有新增的越权依赖；
2. **运行模块与集成测试**：确保测试在全量配置下通过；
3. **核对改动范围**：确认未引入预期外的文件变动。

这种角色划分也可以跨需求复用：当需求 A 处于长耗时测试阶段时，开发实例可以切换到需求 B 的工作区开展编码。

## 五、 实战演练：并发处理三个日常需求

以下还原一个典型的多任务协作过程：

### 任务背景
- **需求 A（业务新特性）**：实现报表中心大文件流式异步导出；
- **需求 B（架构重构）**：解除订单域与用户域的相互交叉依赖；
- **需求 C（突发热修）**：线上订单子单插入异常未抛出导致事务数据不一致。

---

### 操作过程

#### 09:30 - 10:00：开辟工作区与前期分析
- 执行脚本建立 `.worktrees/feat-async-export` 与 `.worktrees/refactor-domain-decouple`；
- 启动 Audit 实例在需求 B 工作区分析依赖，同时在需求 A 工作区生成导出方案。
- **状态**：双线并行，人工核对方案，互不阻塞。

#### 10:15：处理突发热修
- 生产环境出现紧急缺陷，需要尽快修复。
- 处理方式：
  - 需求 A 的 Claude 实例保持在后台运行测试与单测生成；
  - 命令行签出 `.worktrees/hotfix-p0-tx`；
  - 在热修工作区启动专职 Claude 实例，修改异常处理逻辑并补充回归单测。

#### 10:50：热修验证与合入
- 热修工作区内单测通过；
- 提交 commit 并推送到远端 `hotfix/p0-tx` 分支，创建 PR 走发布流程；
- 执行清理命令：
  ```bash
  git worktree remove .worktrees/hotfix-p0-tx
  ```
- **在此期间，需求 A 与需求 B 的代码和工作目录均未受影响。**

#### 11:00 - 12:00：继续推进主线任务
- 回到需求 A 工作区，确认单测与流式导出实现无误；
- 运行 `mvn test -pl report-service`；
- 在测试运行期间，切换到需求 B 工作区，依据之前的审计报告实施包结构解耦；
- 各分支在各自工作区完成验证后，按既定流程合入集成主干。

```text
【单会话串行模式 vs 多工作区并发模式对比】

单会话串行模式:
[ 需求 A 分析 ] ──> [ 需求 A 编码 ] ──> 紧急热修插队 ──> [ 暂存/切分支/重编 ] ──> [ 热修验证 ] ──> [ 切回需求 A 找回上下文 ]
耗时较长，反复打断，编译缓存容易失效

Subagents + Teams + Worktree 并发模式:
Worktree A: [ 需求 A 方案 ] ───────────> [ 需求 A 编码 ] ────────────> [ 后台运行测试 ] ──> 验证合入
Worktree B:        │ [ 需求 B 依赖审计 ] ─────────────────────────────> [ 需求 B 实施解耦 ] ──> 验证合入
Worktree C:        └───────────────────> [ 热修独立开辟 ] ──> [ 快速修复/交付 ] ──> 销毁工作区
各任务在独立物理目录中推进，上下文与构建互不干扰
```

## 六、 潜在代价与挑战：多 Agent 并发的“硬币另一面”

任何架构设计都是权衡的产物。多 Agent 协作与 Worktree 并发固然大幅提升了吞吐效率，但也带来了两个显而易见的现实代价：

### 1. Token 消耗倍增与 API 额度压力
- **多实例的乘数效应**：单会话开发时，一次只会发生一个对话流；而在 3 个 Worktree 并发运行 Claude Code 时，Prompt 读取、多轮工具调用、文件扫描的 Token 开销是成倍叠加的。如果其中一个 Subagent 在深层目录搜索或反复调试测试报错，短短一小时内消耗数百万 Token 是很常见的现象。
- **治理建议**：严格通过 `CLAUDE.md` 限制扫描深度，对 Audit Agent 明确约束输出字数与文件路径白名单，避免无节制的全仓扫描；同时关注平台的速率限制（Rate Limits），防止多实例并发触发 429 报错。

### 2. 人工 Code Review 的认知过载
- **产出速度远超人类审核带宽**：代码生成与修改变快了，但人类工程师的审阅速度并没有同比翻倍。如果同时有 3 个需求分支各自产出几百行改动，原本集中在“编写代码”上的精力，会全部转移到“审查代码”上。当多个 PR 集中推到面前时，人类极易产生审查疲劳，甚至因疲劳而漏过隐蔽的业务漏洞（如并发竞态或边界异常未兜底）。
- **治理建议**：
  - **绝不盲目 Approve**：要求 Agent 在 commit 提单中附带清晰的改动动机（Why）与影响面自查清单；
  - **提升机器裁判权重**：把审查压力前置给自动化断言——严格依赖单元测试、集成测试覆盖率与架构守卫测试（Architecture Guard Tests），让人类的注意力只聚焦在核心业务规则与数据一致性上。

## 七、 多需求并发的实践注意点

在实际推进多分支并发时，还有几项工程细节值得注意：

### 1. 保持分支原子性与独立 PR
避免将多个 Worktree 的代码合并成一个庞大的改动集。每个需求分支保持独立提交，既方便代码审查，也便于线上出现异常时单独回滚。

### 2. 避免本地端口与环境冲突
如果多个需求的集成测试启动了本地端口（如 Mock Server 占用 8080），可以在测试配置中改用随机端口（例如 `server.port=0`），防止两个工作区同时跑测时发生端口冲突。

### 3. 及时清理已合并的工作区
需求合并完成后，及时释放对应的临时目录：
```bash
git worktree remove .worktrees/<worktree-name>
git branch -d <feature-branch>
```
避免本地残留过多废弃的工作区与分支。

## 八、 总结

在小项目或独立实验中，单会话的交互确实轻便快捷。但在涉及多模块、多分支和线上突发情况的企业开发中，单纯依赖单窗口来回切换容易遇到上下文丢失和构建等待的瓶颈。

通过引入：
1. **Subagents**：按需求拆解子任务，保持各任务的上下文独立；
2. **Agent Teams**：将审计、开发与验证阶段拆开，形成流水线接力；
3. **Git Worktree**：在文件系统层面提供相互隔离的并行工作区；

多需求交织时的开发体验可以更加平稳。无论看板上有多少任务穿插，都能在各自独立的工作区中按部就班推进，让自动化辅助真正服务于复杂的工程协作。
